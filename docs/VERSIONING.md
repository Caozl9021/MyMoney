# 版本号与交付节奏规则

2026-11-01 制定。适用于 master 上的 My Money App 交付；独立规则包有自己的版本号，不随 App 版本变化。

## 一句话规则

`versionName` 表示一次对外功能批次，不表示提交次数或构建次数；`versionCode` 每次可安装构建只增不减。没有用户可见变化就不升 `versionName`。

## 版本号含义

| 位 | 含义 | 使用条件 |
| --- | --- | --- |
| MAJOR | 不兼容变更 | 包名/安装身份改变、数据库或备份格式不再兼容、最低系统版本跨越等。必须由用户明确决定。 |
| MINOR | 用户可见功能批次 | 一组相关功能或行为变化完成并准备交付时升一次；多个小改动应合并到同一批次。 |
| PATCH | 修复批次 | 仅用于已经验收通过的版本出现必须单独发布的缺陷修复；不带新功能。 |

`versionCode` 是 Android 安装顺序的唯一依据：每个可安装 APK 递增 1，禁止复用、回退或跳号后回填。文档统一写 `versionName/versionCode`，例如 `1.3.1/115`。

## 什么时候升版本

- **升 MINOR**：一个功能批次完成、验证通过、准备交给用户验收时。开发中、只完成一半或还在反复改界面时不升。
- **升 PATCH**：已验收版本发现必须尽快修复的问题，且不适合并入下一个 MINOR。验收过程中发现的问题不升 PATCH，继续用同一 `versionName` 重建更高 `versionCode` 的候选包。
- **不升 `versionName`**：文档、注释、测试、重构、构建配置、依赖升级、内部调试包、纯规则包更新，以及没有用户可见行为变化的构建。
- **小修合并**：普通 UI 文案、单个边界修复、非关键体验调整，默认并入下一个 MINOR，不单独发 PATCH。
- **只增不减**：已对外出现过的版本号不回退；未验收候选仍在同一 `versionName` 下用新 `versionCode` 继续验证。

## 交付与验收记录

- 一个 `versionName` 对应一个 `deliverables/<versionName>/` 记录；同一版本线的多个候选构建用 `versionCode` 区分，验收记录只在用户明确确认时从“待验收”改为“已验收”。
- 每次候选构建在 manifest / run 记录实际 `versionCode`、APK 摘要、签名和验证范围；最终验收以最后一个通过检查的候选为准。
- `acceptance.md` 只记录该版本线的接受范围与未测边界，不为每个中间构建重复建目录。
- 纯规则更新不创建 App 版本目录，继续使用规则包版本和自己的 Release 记录。

## 交付节奏

默认按“功能批次”交付，不按“每次修改”交付：

1. 需求/方案确认后，在同一条工作线上完成一组相关改动。
2. 测试、构建、设备核验通过后，才确定下一个 `versionName` 并交付用户验收。
3. 验收中修复不新增版本号，只增加 `versionCode`。
4. 验收通过后归档；下一组用户可见功能再升 MINOR。
5. 只有已验收版本的紧急缺陷才使用 PATCH，且 PATCH 不夹带新功能。

## 后续版本

已验收版本之后的新功能批次递增MINOR；验收中的修复沿同一版本线提高versionCode。纯规则包仍使用独立版本号，不随App版本变化。
