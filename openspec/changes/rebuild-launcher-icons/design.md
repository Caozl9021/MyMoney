# 设计决定：图标为什么只能靠"删掉重建"

状态：实施完成，待用户验收。

## 为什么根因是"前景层没生成"而不是"桌面缓存"

三条独立证据指向同一个结论：

1. **文件 mtime 不一致**：`ic_launcher.png` / `ic_launcher_round.png` 是 2026-10-22 13:48（新图），
   而 `ic_launcher_foreground.png` 五档全是 2026-10-21 15:03（旧图），`values/colors.xml` 也是 10-21。
   同一次"换图标"不可能只更新一半文件——是一半根本没人写。
2. **脚本内容**：`generate-icons.sh` 与 `regenerate-icons.sh` 的 magick/convert 输出目标都只有
   `ic_launcher.png`、`ic_launcher_round.png`；全文没有 `ic_launcher_foreground`，也没有写 `colors.xml`。
3. **自适应图标的结构**：`mipmap-anydpi-v26/ic_launcher.xml` 只引用 `@color/ic_launcher_background`
   与 `@mipmap/ic_launcher_foreground`。API 26+ 桌面走这个分支，legacy PNG 只有在没有 anydpi 定义时
   才会被用到。所以"legacy 换了"对真机显示毫无影响。

清缓存、重启桌面都不会改变结论——显示的仍然是 10-21 那张旧前景图。

## 为什么是"全删再生成"而不是"补生成前景层"

补生成只会让新旧图片并存：legacy 已经是新图、前景层补成新图，但 `values/colors.xml` 的旧背景色
（`#C0E1D7` 浅薄荷绿）还在，会在圆形裁切边缘露出一圈薄荷绿。用户明确要求"把原来的图标彻底删掉"，
旧文件留着只会让下一次排查再次误判"文件都在、应该没问题"。删掉后由脚本一次生成全套，任何缺失都会
被脚本自带的校验挡住（尺寸/透明性不符 `exit 1`），不会重演"生成了一半还以为成功"。

## 前景层为什么把白底转透明

源图 `AutoBook-converted.png` 是彩绘 + **纯白底**（直方图 `#FFFFFF` 1,103,569 px，占 14.47%；
四角采样全为 `srgb(255,255,255)`），不是透明背景。直接把整张方图塞进 `foreground` 会得到一个白方块，
在深色壁纸/圆形裁切下非常明显。

转透明的做法是 `-fuzz 5% -transparent white`，同时把自适应背景色也设为 `#FFFFFF`。这样：
前景层在圆/方/圆角矩形裁切下都是"彩绘图形 + 透明边"，而背景层渲染出来的白与原图的白色完全一致，
视觉上无缝。若哪天要换深色背景，只需改 `generate-icons.sh` 的 `BG_COLOR` 并重跑——
脚本会同时重写 `values/colors.xml`，不会出现前景透明区露出错误底色。

`-fuzz 5%` 而非 0：源图 PNG 是有损转码来的，白底并非严格 `#FFFFFF`（存在 `#FEFEFE` 一类近似白），
容差太小会在图形边缘留一圈白毛刺。

## 为什么内容限制在 68dp 安全区（108dp 画布）

自适应图标的名义画布是 108dp，但任何形状的可见区域都不超过中间 **72dp** 的圆。再加图形自身的
留白需求，取 68dp 作为内容外接盒：`INNER = round(CANVAS * SAFE_DP / 108)`，五档分别是
68/102/136/204/272 px。

代价是图标在桌面上看起来会略小一圈（内容占可见圆的比例约 68/72）。这是有意的：宁可小一点，
也不要让图形边缘被圆形/方形/水滴形裁切切掉。若真机上觉得太小，改 `SAFE_DP` 一个数字重跑即可。

## 校验为什么用 `%[opaque]` 而不是 `%[channels]`

ImageMagick 7 的 `%[channels]` 返回 `srgb 3.0` / `srgba 4.0` 这类带位深的值，与 `RGB`/`RGBA`
字符串比较必然全部失败（第一版脚本就踩了这个坑，15 条校验全 ✗ 但文件其实是对的）。
`%[opaque]` 直接返回 `True`/`False`，语义正好是"有没有透明像素"，也正是我们要断言的：
legacy 必须 `True`（不透明），自适应前景必须 `False`（带透明）。

## 刻意不做

- **不放宽 68dp**：这是唯一能在三种裁切形状下都不切边的保守值，看起来"图标偏小"是预期。
- **不做 `mipmap-anydpi-v33` 的 `monochrome` 单色层**：Android 13+ 主题图标需要一份单色矢量素材，
  现在没有，硬把彩图去色会得到一团糊。留作后续。
- **不动 legacy 的圆角**：`ic_launcher_round.png` 目前是方图直接缩放，圆角交给桌面裁切。
  自己画圆角在各家桌面上反而更容易出错。

## 验证边界

- 单测覆盖不到图标——这是纯资源变更，`167` 个单测只能证明代码没被碰坏。
- APK 层面能证明"新图确实进了包"：debug 包五档前景层字节数 8590/14634/20982/35825/53182
  （旧包 3659/6591/10242/20653/34715），release 包 `res/BW.xml` 的 `<foreground>` 指向的 PNG
  实测 432x432 `opaque=False`、中心 `srgba(48,129,250,1)`，`color/ic_launcher_background` = `#ffffffff`。
- ~~**证不了"真机桌面上真的换了"**~~：当时 `adb devices` 为空、本轮禁止读图，所以留作未验证。
  **后续已补上**：2026-10-22 用户装 0.6.4 release 后真机看到白底彩色圆环新图，无需清缓存——这条闭环。
  仍未覆盖的是三种裁切形状下的 68dp 安全区边距（无设备目视）。


## 2026-10-22 留白调整补遗（0.6.5，待验收）

自适应前景内容外接盒从 68dp 缩至 54dp，108dp 画布不变，图案线性缩小约 21%。Legacy 对裁切后的原图按 55% 最大边比例居中放入白色画布，统一视觉占比。校验五档尺寸、透明性、前景 alpha 包围盒与居中情况。保持历史记录，本文补遗优先于历史 68dp 决定。

补充：原图主体最大边 874/1254≈69.7%，legacy 去白边后取55%，相对旧版约缩小21%。原计划75%会导致反向放大，已在生成前纠正。
